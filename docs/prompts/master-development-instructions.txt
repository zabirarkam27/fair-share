## 4. Critical Financial Rules

These rules are non-negotiable.

### Money Representation

- Never use JavaScript floating-point arithmetic for financial calculations.
- Represent money internally as integer poisha.
- ৳1 = 100 poisha.
- Validate that monetary inputs have no more than two decimal places.
- Use PostgreSQL BIGINT or an explicitly safe integer representation for stored poisha.
- Handle JavaScript BigInt serialization correctly.
- Never convert financial amounts into floating-point numbers for business calculations.

### Split Calculation

Implement four split types:

1. EQUAL
2. EXACT
3. PERCENTAGE
4. SHARES

All calculation functions must be pure, independently testable, and deterministic.

EQUAL:
- Divide total poisha by the number of included members.
- Distribute remainder poisha deterministically.
- Rotate remainder priority using a stable expense-specific ordering so the same person does not always receive the extra poisha.

EXACT:
- Every member's specified share must be non-negative.
- The sum of all shares must equal the expense total exactly.

PERCENTAGE:
- Percentages must be valid and sum to exactly 100%.
- Use integer-based percentage representation with adequate precision.
- Calculate shares using integer arithmetic.
- Distribute rounding remainder deterministically.
- The final shares must equal the expense total.

SHARES:
- Each member must have a positive integer share weight.
- Divide the total proportionally.
- Distribute remainder poisha deterministically.
- Final shares must equal the expense total.

### Balance Calculation

For every expense:

- The payer receives credit for the full expense amount.
- Each included member receives a debit equal to their allocated share.
- Excluded members receive no debit.

For every settlement:

- The sender receives a positive balance adjustment.
- The receiver receives a negative balance adjustment.

Define and document one consistent sign convention.

The sum of all member balances in a group must always equal zero.

### Important

Never store a manually editable balance as the financial source of truth.

Calculate balances from expenses and settlements. Use caching only if correctness and invalidation are properly handled.

## 5. Security Rules

Every server-side operation must independently verify:

- Authenticated session
- User identity
- Group membership
- Group role
- Resource ownership
- Group/resource relationship

Never rely on:

- Hidden buttons
- Frontend route protection alone
- Client-provided user IDs
- Client-provided roles
- Client-provided group membership
- Unverified resource IDs

Use the authenticated session as the source of user identity.

A normal member may:
- Add expenses.
- Edit their own expenses.
- Delete their own expenses.
- View authorized group information.

An admin may:
- Perform all group administration actions.
- Edit and delete any group expense.
- Remove members.
- Delete the group.

Validate every mutation with Zod.

Use database transactions for operations that must succeed or fail together.

## 7. Settlement Algorithm

Implement a deterministic debt-settlement algorithm.

Requirements:

- Identify debtors and creditors.
- Match outstanding debts against outstanding credits.
- Generate valid payment suggestions.
- Ensure all suggested payments settle the group's net balances.
- Avoid self-payments.
- Never generate zero or negative payments.
- Use integer poisha only.

Use a greedy settlement strategy for larger groups.

Document honestly that greedy settlement does not guarantee globally minimum transactions in every possible case.

If implementing exact minimum transactions for small groups, use a bounded exact optimization strategy and a documented fallback for larger groups.

Never claim global optimality unless the algorithm actually guarantees it.

## 8. Activity History

Use immutable activity records.

For expense edits:
- Preserve old values.
- Preserve new values.
- Record actor.
- Record timestamp.
- Record the related expense ID.

Deleting an expense must not delete its historical audit records.

Use database transactions for related operations.
